Status: DRAFT revision 4 (after three cross-check reviews), not independently reviewed, not tagged. Nothing here is accepted, weighted or credited, and no other repository may rely on it until it is reviewed and tagged v0.1.0.
Authority: this is the sole normative source for the public command, state, event and backend interfaces. Schemas ([motion-command.schema.json](motion-command.schema.json) and the others) are machine-readable renderings of it; on any conflict this document wins and the schema is corrected. Error codes are defined in [ERROR_CODES.md](ERROR_CODES.md). Rationale is in [MOTION_DECISIONS.md](../architecture/MOTION_DECISIONS.md); architecture is in [MOTION_ARCHITECTURE.md](../architecture/MOTION_ARCHITECTURE.md).

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. A section marked PROVISIONAL depends on an unpinned upstream contract and MUST NOT be frozen in a tagged release until that contract is pinned.

## 1. Conventions and versioning

1.1 The contract version is SemVer. Every submission carries `contract_version`. A MAJOR version the implementation does not support MUST be rejected `UNSUPPORTED_CONTRACT_VERSION`.

1.2 Adding an optional field, a command type or a reserved feature's definition is a MINOR change. Changing a lifecycle transition, unit, limit semantics, error meaning or required field is a MAJOR change and needs a changelog entry and an approved decision.

1.3 Numbers are finite IEEE 754 doubles. NaN and infinities MUST be rejected `NON_FINITE_VALUE`. Durations are integer milliseconds. Timestamps are RFC 3339 UTC with millisecond precision or finer and are used for audit only (section 10).

1.4 Identifiers are case-sensitive strings of 1 to 128 characters from `A-Z a-z 0-9 . _ : -`. `client_request_id` is generated by the client; `command_id`, `event_id` and `fault_id` are generated by Motion and MUST be unique within the deployment.

## 2. Scope and safety boundary

2.1 Motion defines the meaning, validation, execution tracking and termination of motion requests. It MUST NOT define motor control, actuator transport, firmware, sensor acquisition, skill orchestration or physical safety validation.

2.2 Software acceptance of this contract, including unit tests, simulation and mocks, is never physical or safety validation. `STOP`, `HOLD` and `CANCEL` are software motion controls and MUST NOT be described as emergency-stop or certified safety functions. A limit declared in configuration is an enforced software value and is not evidence that a device is safe at that value.

2.3 KOS-MOTION-001 specifies the contract only. It does not include a runtime or simulator.

2.4 Confirmation principle. Motion MUST NOT report a command, joint or backend as stopped, completed, engaged or recovered unless the corresponding execution condition has been confirmed through the Execution Backend Interface or established from valid fresh feedback as specified. Absence of an active command is not evidence that a joint is stopped. Where a condition cannot be confirmed, Motion reports it as unconfirmed and never as success. Three situations are kept apart: (a) an operation rejected at admission or refused by the backend before any termination attempt was accepted is a rejection or a failure with the backend's error code and does not by itself change the joint's control state; (b) a termination attempt that the backend accepted but did not confirm within its bound is `FAILED(TERMINATION_UNCONFIRMED)` and sets control state `UNKNOWN`; (c) if Motion can no longer establish the physical condition for any reason (for example the backend becomes unavailable while the joint was active or terminating), the control state becomes `UNKNOWN` because the condition itself is uncertain, whatever the admission result of any command. The joint state reports what Motion can establish, not the admission result of a command.

## 3. Robot configuration (AD-022, AD-023)

3.1 Robot configuration is versioned and owns, per joint: logical `joint_id` and name, `joint_type` (`revolute` or `prismatic`), positive direction, position limits (`position_min`, `position_max`) or `continuous: true` for a revolute joint without position limits (3.7), `velocity_max`, `acceleration_max` (optional), supported modes (`position`, `velocity`), `max_feedback_age_ms`, `feedback_required`, `feedback_timeout_policy` (3.6), `termination_confirm_timeout_ms`, `degradation_policy` (13.8), `position_tolerance`, `settling_duration_ms`, `default_execution_timeout_ms`, `default_deadline_ms`, and per-fault `clearance` policy (section 13).

3.2 Motion MUST validate configuration completeness and internal consistency before enabling command execution. Until a configuration is validated and active, every submission MUST be rejected `CONFIG_NOT_ACTIVE`.

3.3 Every accepted command MUST record the `config_version` and `config_digest` used at admission. They are immutable for the life of the command. A command MUST NOT be reinterpreted under a newer configuration.

3.4 A configuration update applies only to commands accepted after activation. Motion MUST NOT activate a configuration that is incompatible with a joint's active command, and MUST report the incompatibility explicitly. Activation and rollback are explicit, authorized and traceable operations (permission in section 16).

3.5 Backend capabilities MUST NOT widen limits declared in configuration (section 8).

3.6 Policy vocabularies. Configuration activation MUST fail on an unknown policy value or a policy that the declared backend capabilities cannot satisfy.

| Policy | Values | Rules |
|---|---|---|
| `feedback_timeout_policy` | `STOP_AND_FAULT`, `DEGRADE` | `STOP_AND_FAULT` requires backend controlled-stop support. `DEGRADE` is allowed only when `feedback_required` is false. No value may request `HOLD` as the response to feedback loss |
| fault `clearance` (per fault code) | `CLIENT_AUTHORIZED`, `HUMAN_REQUIRED` | Default `HUMAN_REQUIRED` (13.6) |
| `degradation_policy` (per degradation reason) | list of permitted operations from `SET_POSITION`, `SET_VELOCITY`, `HOLD` | Absent means none permitted. A policy grants permission in principle only; runtime preconditions still apply (13.8). Activation MUST fail on an inherently incompatible combination (13.8) |

3.7 Continuous joints. In v0.1.0 a joint with `continuous: true` supports `velocity` mode only. A configuration that lists `position` mode for a continuous joint is invalid. Position control of continuous joints (including wrap-around and an unwrapped coordinate definition) is reserved for a later MINOR version.

## 4. Targets (AD-002, AD-026)

4.1 A target is `{ "type": <target_type>, "id": <logical id> }`. Targets use logical IDs only. A command MUST NOT reference a motor channel, encoder address, MCU pin or transport ID.

4.2 Target types: `joint` is supported. `joint_group`, `end_effector` and `robot` are RESERVED: they are valid values of the type field and MUST be rejected `UNSUPPORTED_TARGET_TYPE`. An unknown type is `INVALID_SCHEMA`. An unknown ID of a supported type is `UNKNOWN_TARGET`.

4.3 A reserved identifier implies no implementation and no acceptance. A future MINOR version that defines one MUST NOT change the meaning of existing commands.

## 5. Command model (AD-001, AD-003, AD-004, AD-005, AD-016, AD-026)

5.1 Common envelope fields:

| Field | Required | Meaning |
|---|---|---|
| `contract_version` | yes | Version the sender targets |
| `client_request_id` | yes | Idempotency key within the client (section 7) |
| `identity_assertion` | see 16.2 | Identity assertion in the Core-approved format (PROVISIONAL) |
| `command_type` | yes | Operation (5.2) |
| `target` | per type | Logical target (section 4); not used by `CANCEL` |
| `parameters` | per type | Operation-specific values with declared units |
| `constraints` | no | Command limits that narrow configured limits (section 8) |
| `priority` | no | Default level only in v0.1.0 (5.6) |
| `deadline_ms` | no | Latest time execution may start, as a duration from acceptance |
| `execution_timeout_ms` | no | Maximum execution duration after start |
| `issued_at` | no | Client timestamp, audit only |

5.2 Operations:

| `command_type` | Parameters | Meaning |
|---|---|---|
| `SET_POSITION` | `target_position`, `unit` | Move to an absolute position in the configured joint coordinate system |
| `SET_VELOCITY` | `target_velocity`, `unit`, optional `duration_ms` | Move at a signed velocity |
| `STOP` | none | Controlled stop of motion on the target |
| `HOLD` | none | Maintain the current measured position |
| `CANCEL` | `command_id` | Cancel a specific accepted command |
| `CLEAR_FAULT` | `fault_id` | Clear one identified joint fault; `target` is the joint the fault belongs to (13.6) |
| `EXECUTE_TRAJECTORY` | RESERVED | Rejected `UNSUPPORTED_COMMAND` |

Queries (not commands, no `command_id`): `GET_COMMAND_STATUS(command_id)`, `GET_JOINT_STATE(joint_id)`, `GET_COMMAND_HISTORY(filter)`, `GET_FAULTS(filter)`.

5.3 Units. Position is `rad` for a revolute joint and `m` for a prismatic joint. Velocity is `rad/s` and `m/s`; acceleration `rad/s2` and `m/s2`. Every parameter carrying a physical quantity MUST declare `unit`. A unit that does not match the joint type is rejected `UNIT_MISMATCH`. Values are not converted.

5.4 `SET_POSITION` is absolute. It does not mean an offset from the current position. Relative moves are deferred.

5.5 `SET_VELOCITY` is signed. A positive value is the positive configured direction. A zero velocity target is a velocity target and is not `STOP` or `HOLD`. Without `duration_ms` the command stays active until stopped, cancelled, timed out or failed.

5.6 `priority` is an integer. The only accepted value in v0.1.0 is the configured default (0 unless configuration says otherwise). Any other value is rejected `UNSUPPORTED_PRIORITY`. Priority never overrides arbitration (section 9), configured limits or backend capability limits.

5.7 Torque, current and PWM commands are excluded. They are below the Motion abstraction.

## 6. Control and query operations (AD-008, AD-029)

6.1 `CANCEL` references a `command_id` and requests cancellation of that command if it is cancellable and not terminal. It MUST NOT be used to mean "stop all motion". Cancellation eligibility:

| Operation being cancelled | Cancellable |
|---|---|
| `SET_POSITION`, `SET_VELOCITY` | Yes |
| `HOLD` while engagement is pending | Yes; the hold request is terminated and the result is `CANCELLED` once termination is confirmed |
| `HOLD` after engagement is confirmed | No (terminal). Use `STOP` or a new movement |
| `STOP`, `CLEAR_FAULT` | No. Rejected `COMMAND_NOT_CANCELLABLE` |
| `CANCEL` | No. Rejected `COMMAND_NOT_CANCELLABLE` |

A terminal target command is rejected `COMMAND_ALREADY_TERMINAL`. An unknown command, or one the client may not see, is rejected `COMMAND_NOT_FOUND`.

6.2 `STOP` is a target-level operation. It does not depend on whether a movement command is active, and success is never inferred from the absence of an active command (2.4). Receipt of the request MUST NOT be reported as success. Behaviour:

| Joint situation | Behaviour |
|---|---|
| Movement active | Request termination of the active command (9.3); `STOP` completes when termination is confirmed |
| `HOLDING` | Request release of the hold and a controlled stop; completes on confirmation |
| Nothing active, `IDLE` | Request or obtain backend confirmation that the controlled-stop condition holds; completes only on that confirmation |
| `FAULTED` joint | Accepted as an authorized best-effort stop request if the backend can still accept it. Completion does not clear, downgrade or hide the fault |
| Backend unavailable or controlled stop unsupported | Rejected `BACKEND_UNAVAILABLE` or `BACKEND_CAPABILITY_UNSUPPORTED` at admission. This is a rejection, not an unconfirmed termination. If the joint was `ACTIVE`, `HOLDING` or terminating when the backend became unavailable, the control state is `UNKNOWN` under 2.4(c) |

If the backend accepted a termination request but confirmation is not obtained within `termination_confirm_timeout_ms`, `STOP` ends `FAILED(TERMINATION_UNCONFIRMED)` and the joint's control state is `UNKNOWN` (13.2). If the backend refuses the request before accepting a termination attempt, `STOP` ends `FAILED(BACKEND_REJECTED_DISPATCH)` and the control state is changed only as 2.4(c) requires. A `STOP` whose shared termination is confirmed ends `COMPLETED(STOP_CONFIRMED)` even if the joint is, or becomes, `FAULTED`: the fault stays recorded and is not cleared by the stop.

Joining. A `STOP` that arrives while a termination attempt is outstanding on the same joint (started by `CANCEL`, a timeout, a deadline, a fault or another `STOP`) joins that attempt: `STOP_REQUESTED` is appended to its termination record (10.6), the confirmation bound is neither restarted nor extended, no second backend termination request is sent, and the `STOP` has its own `command_id`, lifecycle and history. It completes when the shared attempt is confirmed and fails `TERMINATION_UNCONFIRMED` when the shared attempt is unconfirmed. If the attempt has already reached a terminal outcome (`CONFIRMED` or `UNCONFIRMED`), a later `STOP` is a new operation with a new termination attempt and never modifies the earlier record.

6.3 `HOLD` references a target and uses the current measured position as the hold reference. It requires valid, fresh position feedback, otherwise `FEEDBACK_UNAVAILABLE` or `FEEDBACK_STALE`. Motion MUST NOT assume the last known position is safe to hold. Without declared backend hold support it is rejected `BACKEND_CAPABILITY_UNSUPPORTED`; Motion MUST NOT pretend to hold. `HOLD` is rejected `TARGET_FAULTED` on a faulted joint. A `HOLD` on an already `HOLDING` joint is accepted as a new traceable operation if feedback is valid and fresh, and completes when the backend confirms the hold remains engaged. A second `HOLD` while a first is still pending engagement is rejected `TARGET_BUSY`.

6.4 Queries are read-only, return authoritative current state, are subject to current authorization (section 16), and remain available in every joint health state.

## 7. Submission, idempotency and lifecycle (AD-006, AD-015, AD-028)

7.1 Submission is asynchronous. Admission is synchronous and returns a submission result:

| Field | Meaning |
|---|---|
| `result` | `ACCEPTED` or `REJECTED` |
| `command_id` | Present when accepted |
| `error` | Present when rejected: `code` (see [ERROR_CODES.md](ERROR_CODES.md)), `message`, and the conflicting `target` or `command_id` where applicable |
| `config_version`, `config_digest` | Present when accepted |
| `accepted_at` | UTC audit timestamp, when accepted |
| `idempotent_replay` | True when the result is the stored original result of an earlier identical submission |

7.2 Acceptance does not mean completion and does not mean physical movement has started. Execution then proceeds independently of the submitting client. Every accepted command MUST reach exactly one terminal state.

7.3 A rejected submission is not an accepted command and has no lifecycle. It is recorded in history (section 15) and the same rejection is returned on replay.

7.4 Idempotency. A repeated submission with the same `client_request_id` from the same authenticated client and identical content MUST return the original result and MUST NOT create a second command. The same `client_request_id` with different content MUST be rejected `REQUEST_ID_CONFLICT`. Request identity is scoped to the authenticated client. The idempotency retention period is set by configuration, MUST be stated in the configuration, and MUST be at least as long as the longest effective execution timeout plus the termination-confirmation bound. After retention expires, a reused ID is a new request.

7.5 Public lifecycle states: `ACCEPTED`, `RUNNING`, `COMPLETED`, `CANCELLED`, `FAILED`. Terminal states: `COMPLETED`, `CANCELLED`, `FAILED`. A terminal state never changes.

| From | To | Trigger |
|---|---|---|
| (admission) | `ACCEPTED` | Admission passed (7.1) |
| `ACCEPTED` | `RUNNING` | Backend confirms execution started |
| `ACCEPTED` (phase `NONE`, not dispatched) | `CANCELLED` | Cancellation or `STOP`, and Motion confirms no dispatch occurred |
| `ACCEPTED` | `FAILED` | `DEADLINE_EXPIRED` (after any dispatched start attempt is terminated), backend rejected dispatch, joint or backend fault, or unconfirmed termination (10.6) |
| `RUNNING` | `COMPLETED` | Completion criterion met (section 12) |
| `RUNNING` | `CANCELLED` | Cancellation or `STOP` requested and termination confirmed |
| `RUNNING` | `FAILED` | `EXECUTION_TIMEOUT` with termination confirmed, `TERMINATION_UNCONFIRMED`, joint or backend fault |

Any transition not in this table is invalid and MUST NOT occur. Each transition is recorded once with a timestamp and a `reason_code`. Terminal reason codes are listed in [ERROR_CODES.md](ERROR_CODES.md).

7.6 Execution phases. A non-terminal command has a phase, which is not a lifecycle state and adds no state to 7.5:

| Phase | Meaning | Applies to |
|---|---|---|
| `NONE` | `ACCEPTED`: not yet dispatched. `RUNNING`: running with no termination outstanding | `ACCEPTED`, `RUNNING` |
| `DISPATCH_PENDING` | Dispatched to the backend; start or rejection not yet confirmed | `ACCEPTED` |
| `TERMINATING` | A termination request is outstanding (10.5) | `ACCEPTED`, `RUNNING` |

Rules: before dispatch (`ACCEPTED`, `NONE`) a cancellation or `STOP` completes without backend termination once Motion confirms no dispatch occurred. After dispatch and before start confirmation (`DISPATCH_PENDING`) the command is not safely cancellable by Motion alone: cancellation or `STOP` moves it to `TERMINATING` and requires backend termination confirmation. A late backend start confirmation MUST NOT revive a command that is `TERMINATING` or terminal; it is ignored and recorded.

7.7 A timeout is not a public state. A deadline or execution timeout results in `FAILED` with reason `DEADLINE_EXPIRED` or `EXECUTION_TIMEOUT`.

7.8 `STOP`, `HOLD`, `CANCEL` and `CLEAR_FAULT`, when accepted, receive their own `command_id` and the same public lifecycle and phases. `STOP` and `HOLD` reach `COMPLETED` on confirmation (section 12). `CANCEL` reaches `COMPLETED(CANCEL_EFFECTIVE)` when the target command reaches `CANCELLED`, and `FAILED` with the same reason as the target's `FAILED` outcome otherwise (including a fault code or `TERMINATION_UNCONFIRMED`). Acceptance of a cancellation request is not evidence that cancellation succeeded. `CLEAR_FAULT` reaches `COMPLETED` when the identified fault is cleared.

Ownership. A movement command (or a pending `HOLD`) owns its termination record (10.6). `STOP` and `CANCEL` commands are control operations: they reference a termination attempt, own no execution and have their own lifecycle. Their outcomes are derived from the referenced attempt as in 13.4.

## 8. Limits and validation (AD-013)

8.1 Three limit categories apply: configuration limits (from configuration), command limits (`constraints` in the command) and backend capability limits (declared by the backend). The effective permitted range is the intersection of all that apply.

8.2 Command constraints MAY narrow but MUST NOT widen configured limits. Backend capabilities MUST NOT widen configured limits. Invalid, contradictory or unavailable limits are rejected with an explicit error. Motion MUST NOT clamp a value and report the command accepted.

8.3 Requested values at a limit boundary are inside the limit (limits are inclusive). Values beyond it are rejected `LIMIT_POSITION`, `LIMIT_VELOCITY` or `LIMIT_ACCELERATION`. `SET_POSITION` on a `continuous` joint is rejected `UNSUPPORTED_MODE` (3.7). Backend numerical limits (17.2) take part in the intersection; a backend that declares no narrower numerical limit says so explicitly, and Motion MUST NOT assume a backend supports the whole configured envelope.

8.4 Validation runs in this fixed order and reports the first failure, so results are deterministic:

1. Identity assertion present, valid and unexpired (16.2): else `UNAUTHENTICATED`.
2. Envelope schema, finite numbers, `contract_version` major: `INVALID_SCHEMA`, `NON_FINITE_VALUE`, `UNSUPPORTED_CONTRACT_VERSION`.
3. Authorization for the operation and target scope (16.3): `PERMISSION_DENIED`. A command or fault the client may not see is reported `COMMAND_NOT_FOUND` or `FAULT_NOT_FOUND`, not `PERMISSION_DENIED`, to avoid disclosure.
4. Idempotency lookup (7.4): return the stored result or `REQUEST_ID_CONFLICT`. A stored result is returned only to the same authenticated client that currently passes step 3. Status retrieval separately enforces current read permission.
5. Active configuration (3.2): `CONFIG_NOT_ACTIVE`.
6. Command type, target type, target ID, referenced command or fault: `UNSUPPORTED_COMMAND`, `UNSUPPORTED_TARGET_TYPE`, `UNKNOWN_TARGET`, `COMMAND_NOT_FOUND`, `FAULT_NOT_FOUND`, `COMMAND_ALREADY_TERMINAL`, `COMMAND_NOT_CANCELLABLE`.
7. Joint supports the mode; priority; unit: `UNSUPPORTED_MODE`, `UNSUPPORTED_PRIORITY`, `UNIT_MISMATCH`.
8. Limits and constraints: `LIMIT_*`, `INVALID_CONSTRAINT`, `INVALID_TIMEOUT`.
9. Backend health and capability: `BACKEND_UNAVAILABLE`, `BACKEND_CAPABILITY_UNSUPPORTED`.
10. Joint state and preconditions, with the exemptions in 8.6: `TARGET_STATE_UNKNOWN`, `TARGET_FAULTED`, `TARGET_DEGRADED`, `FEEDBACK_UNAVAILABLE`, `FEEDBACK_STALE`, and the `CLEAR_FAULT` checks (13.6).
11. Arbitration (section 9): `TARGET_BUSY`.

8.5 Runtime feedback MUST continue to be monitored against configured limits during execution. Admission alone does not make execution safe; a limit violation raises a joint fault `JOINT_LIMIT_VIOLATION` (section 13).

8.6 Joint-state exemptions at step 10. Control state is checked independently of health: `SET_POSITION`, `SET_VELOCITY` and `HOLD` MUST be rejected `TARGET_STATE_UNKNOWN` whenever `control_state` is `UNKNOWN`, whatever the health state (a joint can be `UNKNOWN` and `READY`, for example after connecting). That check is made first; the health columns below apply when `control_state` is not `UNKNOWN`. `STOP`, `CANCEL` (for a cancellable command) and queries stay available on an `UNKNOWN` joint, subject to authorization and backend capability, and `CLEAR_FAULT` follows 13.6.

| Operation | On a `FAULTED` joint | On a `DEGRADED` joint |
|---|---|---|
| Queries | Allowed | Allowed |
| `CLEAR_FAULT` | Allowed, subject to 13.6 | Allowed if a fault exists |
| `STOP` | Allowed, best effort (6.2) | Allowed |
| `CANCEL` | Allowed for a cancellable non-terminal command | Allowed |
| `HOLD` | Rejected `TARGET_FAULTED` | Only if `degradation_policy` permits and 6.3 holds |
| `SET_POSITION`, `SET_VELOCITY` | Rejected `TARGET_FAULTED` | Only if `degradation_policy` permits, else `TARGET_DEGRADED` |

## 9. Arbitration, STOP and HOLD (AD-007, AD-016, AD-029, AD-034)

9.1 Two concepts are kept apart: the movement execution slot, which is exclusive per joint, and the persistent joint control condition (`HOLDING`).

| Operation or condition | Occupies the movement slot |
|---|---|
| `SET_POSITION` or `SET_VELOCITY` from acceptance to terminal | Yes |
| `HOLD` while engagement is pending | Yes |
| `HOLDING` after confirmed engagement | No: persistent control condition |
| `STOP`, `CANCEL`, `CLEAR_FAULT` | No. `CLEAR_FAULT` additionally requires no active execution (13.6) |
| Queries | No |

A movement command or `HOLD` arriving while the slot is occupied is rejected `TARGET_BUSY`, identifying the conflicting target and `command_id`. Motion MUST NOT replace, preempt or queue silently. Queuing and replacement are deferred and need an explicit policy.

9.2 Commands on independent joints MAY run concurrently subject to backend capacity. Multi-joint coordination is RESERVED.

9.3 `STOP` never competes for the slot and is never rejected `TARGET_BUSY`. If movement is active, it explicitly terminates the active command: the command enters the termination phase with cause `STOP_REQUESTED` and, once termination is confirmed, ends `CANCELLED` with reason `STOPPED`. This is explicit preemption, not silent preemption. If a termination is already outstanding, `STOP` joins it (6.2). `STOP` is subject to authorization (16.3) and backend capability.

9.4 `CANCEL` and `CLEAR_FAULT` do not compete for the slot.

9.5 A movement command accepted while the joint is `HOLDING` passes the other preconditions and, when it starts, explicitly releases the hold through the backend interface. If the release fails, the command ends `FAILED(BACKEND_REJECTED_DISPATCH)` and the hold state is re-evaluated from backend confirmation, not assumed. `STOP` also ends a hold. A hold that fails or loses valid feedback follows section 13.

## 10. Time, timeouts and termination (AD-009, AD-027, AD-032)

10.1 Clock domains:

| Time information | Clock |
|---|---|
| Audit timestamps (`issued_at`, `accepted_at`, history, events) | Wall-clock UTC |
| Command deadline | Duration from acceptance, measured on Motion's monotonic clock |
| Execution timeout | Duration from confirmed start, measured on Motion's monotonic clock |
| Feedback freshness | Motion's monotonic receipt time |
| Backend measurement timestamp | Backend clock; MUST declare its clock domain and synchronization status |

10.2 Motion MUST record both the backend measurement timestamp and its own receipt time for every feedback sample. It MUST NOT compare timestamps from unsynchronized clocks to decide freshness.

10.3 Command deadline: if execution has not started within `deadline_ms` of acceptance, the command ends `FAILED` with reason `DEADLINE_EXPIRED`. If it was already dispatched, termination with cause `DEADLINE_EXPIRED` is requested and confirmed first (10.5, 10.6). If `deadline_ms` is absent, the configured default applies; the effective value is recorded in the command record.

10.4 Execution timeout: if a running command has not reached a terminal state within `execution_timeout_ms` of confirmed start, Motion requests termination with cause `EXECUTION_TIMEOUT`. Absent a value, the configured default applies, including an explicit configured "no timeout". The effective value is recorded.

10.5 Termination. A termination request has a cause (`CANCEL_REQUESTED`, `STOP_REQUESTED`, `EXECUTION_TIMEOUT`, `DEADLINE_EXPIRED`, `FAULT`). Motion sends a termination request to the backend and starts a bounded wait of `termination_confirm_timeout_ms` (configuration; MUST be finite). A timeout request is not confirmation that motion has stopped; Motion MUST distinguish timeout detection from confirmed termination.

10.6 Termination record. A command in the termination phase carries a termination record: the initial cause, any additional causes in order, the request time, the confirmation bound and the outcome (`PENDING`, `CONFIRMED`, `UNCONFIRMED`). Rules:

1. The first termination request starts the bounded wait. Additional causes, including faults, are appended and MUST NOT restart or extend the bound.
2. If termination is confirmed, the outcome reflects the most consequential cause: a `FAULT` gives `FAILED` with the fault code (the first fault if several); otherwise `EXECUTION_TIMEOUT` or `DEADLINE_EXPIRED` give `FAILED` with that reason (if both are recorded, the one recorded first); only when every cause is `CANCEL_REQUESTED` or `STOP_REQUESTED` does the command end `CANCELLED`, with reason `STOPPED` if any `STOP_REQUESTED` cause is present and `CANCEL_REQUESTED` otherwise. Causes are ordered by the time Motion appended them.
3. If confirmation does not arrive within the bound, the command ends `FAILED(TERMINATION_UNCONFIRMED)`, the joint is faulted with `TERMINATION_UNCONFIRMED`, its control state is `UNKNOWN`, and Motion MUST NOT report the joint as stopped.
4. All causes and fault IDs remain in history. A cancellation request recorded before a fault stays in the record.
5. Operations referencing the attempt (`STOP`, `CANCEL`) derive their outcomes from it as in 13.4. A fault never converts a confirmed `STOP` into a failed `STOP`.

## 11. Feedback (AD-010, AD-011)

11.1 A joint feedback record has `measured_position`, `measured_velocity`, `backend_timestamp` with `clock_domain`, `received_at` (Motion monotonic receipt time, exposed as an offset or sequence, plus UTC for audit), `validity`, `source` and `backend_status`.

11.2 Commanded values and measured values are separate. Invalid feedback MUST NOT be presented as valid measured state. Missing feedback is represented explicitly.

11.3 Feedback status per joint is `VALID`, `STALE` (older than `max_feedback_age_ms` by receipt time), `INVALID` (backend marked invalid) or `MISSING`. Backend health and feedback validity are independent properties.

11.4 Commands that depend on current position or velocity (`HOLD`, completion evaluation) MUST NOT rely on stale or invalid feedback.

11.5 Loss of required feedback during execution (`feedback_required = true`) raises joint fault `FEEDBACK_LOST` and requests a controlled stop through the backend if supported. The response is governed by `feedback_timeout_policy` (3.6) and declared backend capabilities; Motion MUST NOT assume `HOLD` is safe. If feedback is not required, the joint's health becomes `DEGRADED` (reason `FEEDBACK_OPTIONAL_UNAVAILABLE`) and the running command and others permitted by `degradation_policy` (13.8) continue.

## 12. Completion (AD-012)

12.1 Commanded values never establish completion. A command that cannot establish its completion condition MUST NOT be reported `COMPLETED`.

12.2 Completion conditions:

| Operation | Completed when |
|---|---|
| `SET_POSITION` | Valid, fresh measured position stays within `position_tolerance` of the target for `settling_duration_ms` |
| `SET_VELOCITY` with `duration_ms` | The duration has elapsed on Motion's monotonic clock from confirmed start with no fault |
| `SET_VELOCITY` without duration | Never completes by itself; ends by stop, cancel, timeout or fault |
| `STOP` | Backend confirms the controlled-stop condition (also when nothing was active) |
| `HOLD` | Backend confirms hold engagement, or confirms it remains engaged for a repeated `HOLD` |
| `CANCEL` | The referenced command reached `CANCELLED` |
| `CLEAR_FAULT` | The identified fault is cleared (13.6) |

12.3 Position tolerance and settling duration come from configuration (per joint or execution profile).

## 13. Faults and joint state (AD-014, AD-030)

13.1 Three fault classes are independent: command errors (admission rejection, individual command), joint faults (`FEEDBACK_LOST`, `TRACKING_ERROR`, `JOINT_LIMIT_VIOLATION`, `TERMINATION_UNCONFIRMED`) and backend faults (`BACKEND_UNAVAILABLE`, `BACKEND_COMMUNICATION_LOSS`, `BACKEND_EXECUTION_FAILURE`). `FAILED` describes a command outcome. `FAULTED` describes a joint's health. They are separate state models and MUST NOT be merged.

13.2 Joint state has two independent dimensions.

| Dimension | Values | Meaning |
|---|---|---|
| `control_state` | `IDLE`, `ACTIVE`, `HOLDING`, `UNKNOWN` | `IDLE`: no movement, stop confirmed. `ACTIVE`: a movement command is running. `HOLDING`: hold engagement confirmed. `UNKNOWN`: motion status cannot be confirmed (for example after an unconfirmed termination) |
| `health_state` | `READY`, `DEGRADED`, `FAULTED` | `READY`: available. `DEGRADED`: operating with a declared limitation. `FAULTED`: not available for ordinary motion commands |

Joint state is reported as the pair, so a running command is never hidden by a health change.

13.3 Transitions. Control: `IDLE` to `ACTIVE` when a movement command starts; `ACTIVE` to `IDLE` when it ends with confirmed stop or completion and no hold is engaged; `IDLE` to `HOLDING` on confirmed hold; `HOLDING` to `ACTIVE` when a movement command starts, or to `IDLE` after a confirmed stop; any state to `UNKNOWN` when motion status can no longer be confirmed; `UNKNOWN` to `IDLE` only on a confirmed stop (13.9). Health: `READY` to `DEGRADED` on a declared limitation and back when it clears (control state is preserved); any state to `FAULTED` on a joint or backend fault; `FAULTED` to `READY` only through `CLEAR_FAULT`, or to `DEGRADED` if a degradation condition remains.

13.4 On a joint or backend fault Motion MUST: request a stop through the backend if supported and not already confirmed; append cause `FAULT` to the termination record of every non-terminal movement command (and pending `HOLD`) on each affected joint, starting a termination attempt if none is outstanding, so each ends `FAILED` with the fault code or `TERMINATION_UNCONFIRMED` (10.6); derive the outcome of control operations from that attempt as in the table below; set each affected joint's health to `FAULTED`; publish a fault event; and reject ordinary motion commands on those joints `TARGET_FAULTED` (exemptions in 8.6). A fault affecting several joints MUST be propagated to every affected command record.

| Command on the affected joint | Outcome when the fault occurs |
|---|---|
| Movement command, `HOLD` pending engagement | `FAILED` with the first fault code once the shared termination is confirmed, or `FAILED(TERMINATION_UNCONFIRMED)` if the bound expires. A pending `CANCEL` request does not make it `CANCELLED` |
| `CANCEL` referencing it | `FAILED` with the same reason as its target |
| `STOP` outstanding | Joins the attempt (6.2): `COMPLETED(STOP_CONFIRMED)` when confirmed even though the joint is `FAULTED`; `FAILED(TERMINATION_UNCONFIRMED)` if unconfirmed |
| `CLEAR_FAULT` accepted but not yet applied | Accepted only when no movement or termination was active (13.6). If a new fault or termination begins after acceptance and before the atomic clearance, it ends `FAILED` with the new fault code; neither fault is cleared |
| Confirmed `HOLD` (`HOLDING`) | Not a command in flight; the hold is released by the stop, health becomes `FAULTED`, control state follows confirmation |

The termination bound is neither restarted nor duplicated by a fault. Interrupted commands MUST NOT resume after recovery. A backend fault creates a joint fault record on each affected joint. The backend fault condition ends when the backend reports healthy (event `BACKEND_FAULT_CLEARED`); that does not clear the joint fault records.

13.5 State reported after a fault: the joint record reports `health_state = FAULTED`, the `control_state`, the `fault_ids`, `feedback_status`, and the last valid `measured_position` and `measured_velocity` with `last_valid_feedback_at` and `is_current`. `is_current` is true only when the feedback is valid and fresh under the configured freshness policy; otherwise it is false. When `is_current` is false the measured values are last-known values only and MUST NOT be presented as current.

13.6 `CLEAR_FAULT` clears one identified joint fault. The `target` is the joint and `fault_id` MUST resolve to a fault record on that joint, otherwise `FAULT_NOT_FOUND`. It is explicit and authorized (16.3), never automatic. It is accepted only when: the fault's cause is resolved, the backend is `AVAILABLE`, feedback is valid and fresh where required, `control_state` is not `UNKNOWN`, and no movement command or termination is active on the joint (otherwise `FAULT_NOT_CLEARABLE`). A successful `CLEAR_FAULT` clears only the identified fault; the joint's health returns to `READY` only when no other fault or degradation condition remains. Each fault carries a `clearance` policy from configuration: `CLIENT_AUTHORIZED` (a client with the clear permission may clear it) or `HUMAN_REQUIRED` (the identity assertion MUST carry a human-operator attribute defined by the Core security contract; otherwise rejected `HUMAN_CONFIRMATION_REQUIRED`, and no client can clear it until Core provides a verifiable assertion). Acceptance boundary: the preconditions are evaluated at admission and re-evaluated atomically at the moment Motion applies the clearance. Clearing is a Motion-internal state change in v0.1.0 and needs no backend acknowledgement; the only window is between acceptance and that atomic point. If a new fault or a termination begins in that window, the `CLEAR_FAULT` ends `FAILED` with the new fault's code and neither the new fault nor the targeted fault is cleared. `CLEAR_FAULT` applies only to a joint with a fault record: a joint that is `UNKNOWN` without a fault record has nothing to clear and recovers under 13.9. A fault with no configured policy is `HUMAN_REQUIRED`. Which faults may be set `CLIENT_AUTHORIZED` is an open item for the safety reviewer (section 19).

13.7 Joint and backend state changes are reported as events (section 14).

13.8 Degradation. Every degradation reason (`FEEDBACK_OPTIONAL_UNAVAILABLE`, `BACKEND_DEGRADED`) has a `degradation_policy` in configuration listing which of `SET_POSITION`, `SET_VELOCITY` and `HOLD` remain permitted. No unspecified degradation permits movement. Queries stay available and `STOP` stays available as a best-effort operation. `HOLD` additionally requires valid fresh position feedback and backend hold support, whatever the policy says.

Policy permission versus runtime admissibility. A `degradation_policy` grants permission in principle. Runtime preconditions still apply to every permitted operation: `SET_POSITION` MUST NOT be accepted when its required position feedback is unavailable or stale, because completion is established only from valid fresh measured feedback (section 12); `HOLD` MUST NOT be accepted without valid fresh position feedback; `SET_VELOCITY` is accepted under degradation only when its completion evidence (section 12) remains available, and is never reported complete without it. Configuration validation never replaces these live checks: they are made on every admission. Configuration activation MUST fail when a policy lists, for the reason `FEEDBACK_OPTIONAL_UNAVAILABLE`, `SET_POSITION` or `HOLD`, since those cannot meet their completion or precondition rules without that feedback.

13.9 Establishing and recovering control state.

1. Initial state. When Motion loads a configuration or connects to a backend, each joint's `control_state` is `UNKNOWN` until the backend confirms a state. Motion MUST NOT assume `IDLE` because no command is recorded.
2. A fresh authoritative backend status report MAY establish `IDLE`, `ACTIVE` or `HOLDING` only when it is bound to the joint, identifies the execution or hold condition, and meets the freshness rules of section 11. If the report is partial, ambiguous or stale, the state stays `UNKNOWN`.
3. Ordinary motion is never accepted while `control_state` is `UNKNOWN`, whatever the health state (8.6). Initial `UNKNOWN` is normal initialization: it is not a fault, creates no fault record and needs no `CLEAR_FAULT`; a joint starts `UNKNOWN` and `READY`.
4. Recovery of an `UNKNOWN` joint with no fault record (health `READY` or `DEGRADED`): either a fresh authoritative backend status report meeting item 2 establishes the state, or an authorized `STOP` is confirmed by the backend and establishes `IDLE`.
5. Recovery of an `UNKNOWN` joint that is `FAULTED`: the backend becomes available, an authorized `STOP` is issued, the backend confirms the stopped condition, `control_state` becomes `IDLE`, then an authorized `CLEAR_FAULT` (13.6) clears an eligible fault. A status report alone establishes the control state but never clears a fault. The backend becoming available never moves a joint from `UNKNOWN` to `READY` or `IDLE` by itself.
6. If the backend cannot confirm a stop, the joint remains `FAULTED` and `UNKNOWN` and unavailable for ordinary motion. This is a safety lockout, not a defect to bypass. Any maintenance or physical-intervention recovery is outside this contract and needs a separately specified mechanism with its own authority and evidence; `CLEAR_FAULT` is not an override.

## 14. Status, notifications and events (AD-018, AD-019, AD-031)

14.1 `GET_COMMAND_STATUS` is mandatory and returns the authoritative state: `command_id`, `operation`, `target`, `state`, `phase`, `termination` (the termination record, 10.6), `reason_code`, `config_version`, `config_digest`, effective timeouts, timestamps and `last_sequence_number`.

14.2 Lifecycle notifications and execution events are supported through an abstract event interface. The contract names no transport and MUST NOT depend on ROS 2, DDS, MQTT or gRPC. Notification delivery MUST NOT be required for execution to continue.

14.3 Every event has a unique `event_id`, a `stream` (kind and identifier), a `sequence_number`, `occurred_at` (UTC audit) and `event_type`. Streams:

| Stream kind | Identifier | Events |
|---|---|---|
| `command` | `command_id` | `COMMAND_STATE_CHANGED`, `COMMAND_PHASE_CHANGED` |
| `joint` | `joint_id` | `JOINT_STATE_CHANGED`, `FEEDBACK_STATUS_CHANGED`, `JOINT_FAULT_RAISED`, `JOINT_FAULT_CLEARED` |
| `backend` | `backend_id` | `BACKEND_HEALTH_CHANGED`, `BACKEND_FAULT_RAISED`, `BACKEND_FAULT_CLEARED` |

14.4 Sequence numbers increase monotonically by one within a stream. A client detects a gap by a skipped number. The event interface provides at-least-once delivery where the selected implementation supports it; otherwise delivery may be best effort. Clients MUST tolerate duplicates, detect gaps where sequence continuity is provided, and MUST recover from gaps or lost notifications by querying state, which is authoritative.

14.5 Command and joint events retain the originating client identity where applicable. Events MUST NOT be the sole source of any state.

## 15. Command history (AD-017)

15.1 Motion maintains a queryable record per submission: `client_id`, `client_request_id`, `command_id` (if accepted), operation and target, `submitted_at`, `accepted_at`, `execution_started_at`, `completed_at`, `lifecycle_history` (state, phase, reason, timestamp), `validation_result`, `result`, `fault_references`, `backend_reference`, `config_version`, `config_digest`, `authorization_outcome` and the effective deadline and timeouts.

15.2 History distinguishes rejected from accepted submissions, never silently overwrites an earlier result, has configurable retention, and does not assume permanent storage. High-frequency telemetry is stored separately.

## 16. Authentication and authorization (AD-020, AD-021) — PROVISIONAL

16.1 Platform security owns authentication, credential verification, identity establishment and identity lifecycle. Motion MUST NOT implement credential management.

16.2 Every submission and query MUST carry an identity assertion in the format of the approved Kritva Core security contract. This contract MUST NOT define a competing format. A missing, invalid or expired assertion is rejected `UNAUTHENTICATED`. The assertion's schema in this repository is an opaque object until the Core interface is pinned.

16.3 Authorization is permission-based, not by component identity, and is evaluated on both the operation and the target scope before acceptance or execution. Provisional permissions:

| Permission | Allows |
|---|---|
| `motion.command.submit` | Submit movement commands (`SET_POSITION`, `SET_VELOCITY`) |
| `motion.command.query.own` | Query own commands |
| `motion.command.query.all` | Query all commands |
| `motion.command.cancel.own` | Cancel own commands |
| `motion.command.cancel.all` | Cancel commands of other clients |
| `motion.target.stop` | `STOP` |
| `motion.target.hold` | `HOLD` |
| `motion.state.read` | Read joint and backend state |
| `motion.fault.clear` | `CLEAR_FAULT` |
| `motion.config.activate` | Activate or roll back configuration |
| `motion.admin` | Other privileged operations |

Names are PROVISIONAL and not frozen in the schemas until the Core security interface is pinned.

16.4 Motion MUST NOT assume a client is authorized because it is an internal Kritva component. Every command and event retains the originating client identity. Authorization decisions, including denials, are auditable and recorded in history.

## 17. Execution Backend Interface (AD-024, AD-025, AD-033)

17.1 Motion owns and versions this interface; the Kritva actuator family and the simulator implement it. An implementation MUST NOT redefine Motion contract semantics. Motion MUST reach backends only through this interface.

17.2 A backend MUST declare capabilities: supported target types, supported joint types, supported modes, controlled stop (yes or no), position hold (yes or no), feedback availability (position, velocity), feedback rate or range, execution cancellation, maximum concurrent executions, backend health (`AVAILABLE`, `DEGRADED`, `UNAVAILABLE`, `FAULTED`), per-joint numerical limits (position range, maximum velocity, maximum acceleration where supported, or an explicit declaration that no narrower limit applies), and the clock domain and synchronization status of its timestamps.

17.3 Motion MUST validate requested operations against declared capabilities before dispatch.

17.4 Interface operations (abstract, transport-independent):

| Operation | Purpose |
|---|---|
| `describe_capabilities()` | Return the capability declaration |
| `dispatch(execution_request)` | Start execution of a validated command with its configuration snapshot reference; returns accepted or rejected with a backend reason and a `backend_reference`; start is later reported by `execution_started` or `execution_rejected` (17.5) |
| `request_termination(backend_reference, cause)` | Request controlled termination |
| `confirm_termination` (event or poll) | Report confirmed termination of an execution or controlled-stop condition |
| `request_hold(joint_id)` / `release_hold` | Request or end a hold, if supported |
| `feedback` (stream or poll) | Return feedback records (11.1) |
| `health()` | Return backend health and faults |

17.5 Termination semantics. The interface distinguishes `termination_request_accepted` (the backend accepted the request), `termination_confirmed` (the backend confirms the identified execution has reached its declared termination condition) and `termination_unconfirmed` (no confirmation within the bound, determined by Motion). Confirmation is bound to a `backend_reference` and a logical target. Receipt of a request MUST NOT be equated with confirmation. A partial or unknown outcome is treated as unconfirmed unless confirmation is later given within the bound. Backend confirmation is software-interface evidence and is not proof of physical stopping or certified safety. Start reporting uses `execution_started` and `execution_rejected`, bound to the same `backend_reference`; a start report after termination was requested does not change the command's phase.

17.6 The backend reports capability, execution status, feedback and confirmations. It does not own command-level policy: arbitration, validation, lifecycle and timeouts belong to Motion.

17.7 Simulation levels (S1 contract simulation; S2 joint dynamics; S3 robot kinematics and dynamics) are future implementation work. Simulation results are software evidence and MUST NOT be reported as physical validation. Actuator interface conformance means software contract compatibility only.

## 18. Reserved and excluded (AD-026)

Reserved (valid identifiers, always rejected `UNSUPPORTED_*` in v0.1.0): `joint_group`, `end_effector`, `robot` targets; `EXECUTE_TRAJECTORY`; multi-joint coordination; priority levels other than the default; queuing and replacement policies; relative position commands; position control of continuous revolute joints. Excluded: torque, current and PWM commands; motor control; sensor acquisition; skill planning.
